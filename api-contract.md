# API Contract — Frontend ↔ FastAPI

**Status:** a proposal written by the frontend for Phase 0.
- Items marked **[CONFIRM]** need a backend decision before the phase that uses them.
- Everything here maps 1:1 to `src/types/api.ts` and `src/api/endpoints/*`.

---

## 1. Conventions

- **Base path:** `/api/v1`
- **Format:** JSON, UTF-8, `snake_case` on the wire. The frontend keeps `snake_case` in DTO types and does not transform keys.
- **Auth:** `Authorization: Bearer <Kinde access token>`
  - The backend validates the token's signature against Kinde JWKS, plus its `iss` (Kinde domain), `aud` (API audience) and `exp`.
  - The user identity is the token's `sub`.
- **IDs:** opaque strings (UUID or ULID). Timestamps are ISO-8601 UTC (`2026-09-24T07:00:00Z`).
- **Tracing:** the client sends `X-Request-Id`, and the server echoes it (or its own ID) in the response headers and in error bodies.
- **Pagination:** cursor-based.
  ```json
  { "items": [...], "next_cursor": "opaque" | null }
  ```
  Query params are `?cursor=&limit=` (default 20, max 100).
- **CORS:** allow the frontend origin, the `Authorization`, `Content-Type` and `X-Request-Id` headers, and expose `X-Request-Id`.

## 2. Error envelope

Every non-2xx response has this body:

```json
{
  "error": {
    "code": "conversation_not_found",
    "message": "Human-readable message safe to show",
    "details": { "field": "reason" },
    "request_id": "c0a8…"
  }
}
```

| HTTP | `code` examples | Frontend behaviour |
|---|---|---|
| 400/422 | `validation_error` | Inline message; `details` maps fields (the FastAPI 422 is wrapped into this shape) |
| 401 | `unauthenticated`, `token_expired` | Refresh the token once and retry, then send the user to login |
| 403 | `forbidden` | Toast |
| 404 | `*_not_found` | Not-found view / remove from list |
| 409 | `duplicate_client_message_id` | Treat as success; refetch |
| 413 | `audio_too_large` | Recorder error message |
| 415 | `unsupported_audio_format` | Recorder error message |
| 429 | `rate_limited` (+ `Retry-After`) | Disable send and show a countdown |
| 5xx | `internal_error`, `upstream_unavailable` | Retry affordance |

## 4. Endpoints

### 4.1 User
| Method | Path | Notes |
|---|---|---|
| GET | `/me` | Returns `User`. Upserts the user from the token claims on first call. |

### 4.2 Conversations
| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/conversations?cursor=&limit=` | – | `Page<Conversation>`, sorted by `updated_at desc` |
| POST | `/conversations` | `{ title?: string }` | `201 Conversation` |
| GET | `/conversations/{id}` | – | `Conversation` |
| PATCH | `/conversations/{id}` | `{ title }` | `Conversation` |
| DELETE | `/conversations/{id}` | – | `204` |

- The title is auto-generated by the backend after the first exchange.
- A new title is announced in the stream via a `conversation.updated` event.

### 4.3 Messages
| Method | Path | Notes |
|---|---|---|
| GET | `/conversations/{id}/messages?before=<message_id>&limit=` | `Page<Message>`, **newest first**. The UI reverses it. `next_cursor` is used for older pages. |
| POST | `/conversations/{id}/messages` | **Streaming.** See §5. |
| POST | `/conversations/{id}/messages/{message_id}/cancel` | Stops generation of that assistant message. `202`. Idempotent. |
| POST | `/conversations/{id}/messages/{message_id}/regenerate` | Streaming (same format as §5). Replaces the assistant message. [CONFIRM] |

**Send body:**

```json
{
  "client_message_id": "uuid-from-client",
  "kind": "text",
  "content": "Design a national AI strategy…",
  "audio_id": null,
  "model": "lam13",
  "effort": "medium"
}
```

- `kind: "voice"` requires `audio_id` (from §4.4), and `content` is omitted. The server transcribes the audio.
- `kind: "text"` may carry `attachment_ids: string[]` (from §4.7, at most 6). Unknown or expired ids → `422 attachment_not_found` before the stream opens. [CONFIRM]
- **Markdown:** assistant content is CommonMark + GFM. A single newline is a soft break (rendered as a space); separate paragraphs with a blank line and use list/table syntax for structure. The client does not treat single newlines as line breaks.
- `model` and `effort` are optional. [CONFIRM] whether the backend exposes them via `GET /models`.
- **Lazy conversation creation:** `POST /conversations/new/messages` creates the conversation and emits `conversation.created` first. The alternative is for the client to call `POST /conversations` before sending. [CONFIRM], with the lazy version preferred.

### 4.4 Audio (voice notes)
| Method | Path | Notes |
|---|---|---|
| POST | `/audio` | `multipart/form-data`. Returns `201 AudioRef`. |
| GET | `/audio/{id}` | Returns `AudioRef` with a fresh `url`. Used when a signed URL has expired. |

The `/audio` upload has these fields:
- `file`: the recording. Accepted types are `audio/webm` (opus), `audio/mp4`, `audio/ogg`, `audio/mpeg` and `audio/wav`.
- `duration_ms`: an int measured by the client (the server may re-measure).
- `conversation_id`: optional.

Limits: **max 25 MB and 5 minutes** [CONFIRM]. Over the limit the server returns `413 audio_too_large`.

### 4.5 Voice calls (Vapi)
| Method | Path | Notes |
|---|---|---|
| POST | `/calls` | Body `{ conversation_id }`. Returns `201 CallSession`. The backend chooses the assistant and config. |
| GET | `/calls/{id}` | Returns `CallSession` plus `status: 'pending'\|'active'\|'ended'`, `duration_ms` and `ended_reason`. |
| POST | `/webhooks/vapi` | **Server-to-server only (Vapi → FastAPI).** The frontend never calls it. |

How the call is wired:
- The frontend starts the call with the returned `public_key` / `assistant_id` / `assistant_overrides` and passes `metadata.call_session_id`.
- The backend verifies the Vapi webhook secret.
- On `end-of-call-report`, the backend appends a `Message { kind: 'call_transcript' }` to the conversation.
- The frontend refetches messages when the call ends.
- **[CONFIRM]** Whether the Vapi assistant should use our backend as a *custom LLM* (so the voice agent shares conversation memory) or Vapi's hosted model with a system prompt.

### 4.6 Models (optional)
| Method | Path | Returns |
|---|---|---|
| GET | `/models` | `{ items: [{ id, label, efforts: ['low','medium','high'], default_effort }] }` |

The composer hides its model and effort chips if this endpoint returns `404` or a single model with no efforts.

### 4.7 Image attachments [CONFIRM]
| Method | Path | Notes |
|---|---|---|
| POST | `/attachments` | `multipart/form-data`: `file`, `filename`, optional `conversation_id`. Returns `201 AttachmentRef`. `413 image_too_large` (> 10 MB), `415 unsupported_image_format` (PNG, JPEG, WebP, GIF only). |

- Uploads happen when the user sends; the client then sends the message with `attachment_ids`.
- The client pre-checks type, size and count for fast feedback; **the server is the validation boundary** (sniff content, strip metadata, enforce limits).

### 4.8 Message feedback [CONFIRM]
| Method | Path | Notes |
|---|---|---|
| PUT | `/conversations/{id}/messages/{message_id}/feedback` | Body `{ rating: 'up' \| 'down' \| null }` (`null` clears). Returns `{ message_id, rating }`. Idempotent. `422` for non-assistant or incomplete messages. |

- A regenerated answer starts unrated.

### 4.9 Generated artifacts (PowerPoint, Excel) [CONFIRM]
| Method | Path | Notes |
|---|---|---|
| GET | `/artifacts/{id}` | Current `Artifact`. |
| GET | `/artifacts/{id}/download` | `{ url, expires_at }` — a fresh download reference (signed URLs expire). |

- Artifacts are created by the server while it answers and reported on the message stream as `artifact` events (§5). The final message in `done` lists them.

## 5. Streaming protocol

**Request:** `POST /conversations/{id}/messages` with the headers `Accept: text/event-stream` and `Content-Type: application/json`.

**Response:** `200` with `Content-Type: text/event-stream`, `Cache-Control: no-cache` and `X-Accel-Buffering: no`.
- Validation and auth errors happen **before** the stream opens, as a normal JSON error (§2).
- Each event has the form `event: <type>`, `id: <seq>` and `data: <json>`, followed by a blank line.
- The server sends `: ping` comments every 15s.

| `event` | `data` | Meaning |
|---|---|---|
| `conversation.created` | `Conversation` | Only for lazy creation |
| `message.created` | `{ user_message: Message, assistant_message: Message }` | Server IDs (reconciled with `client_message_id`). The assistant message has `status: 'streaming'` and `content: ""`. |
| `transcript` | `{ message_id, text }` | Voice input: final transcript of the user's audio |
| `status` | `{ state: 'thinking' \| 'solving' \| 'answering' \| 'tool', label?: string }` | Header status ("Thinking…", "Solving…", "Answering…"). `solving` is optional — the client shows it only when sent. Unknown states display as "Thinking…". |
| `delta` | `{ message_id, text }` | Append `text` (Markdown fragment) to the assistant message |
| `conversation.updated` | `{ id, title }` | Auto-title |
| `artifact` | `Artifact` | A deliverable was created or changed (progress, ready, error). The full object, upserted by `id`. [CONFIRM] |
| `done` | `{ message: Message, usage?: { input_tokens, output_tokens } }` | Final, authoritative assistant message (`status: 'complete' \| 'cancelled'`) |
| `error` | `{ code, message, retryable: boolean }` | Terminal. The partial content is kept, with `status: 'error'`. |

**Rules:**
- The **first event is always `message.created`**, or `conversation.created` followed by `message.created`.
- The **last event is always `done` or `error`**.
- `delta.text` is a raw substring, and the concatenation of all deltas equals `done.message.content`. The client may replace its accumulated text with `done.message.content`.
- **Cancellation:** a client disconnect *or* `POST …/cancel` must stop the generation. If the connection is still open, the server ends with `done` and `status: 'cancelled'`.
- **Reconnection** [CONFIRM, optional]:
  - `GET /conversations/{id}/messages/{message_id}/stream` with `Last-Event-ID` replays events after that ID while generation is in progress.
  - If generation has finished, it returns `409 not_streaming`, and the client simply refetches the message.
- **Fallback:** if the backend prefers NDJSON, it sends `Content-Type: application/x-ndjson` with one `{ "event": "...", "data": {...} }` object per line. The client supports both formats. SSE is preferred.

**Example:**

```
event: message.created
id: 1
data: {"user_message":{"id":"m_1","client_message_id":"c_9",...},"assistant_message":{"id":"m_2","status":"streaming","content":"",...}}

event: status
id: 2
data: {"state":"thinking"}

event: status
id: 3
data: {"state":"answering"}

event: delta
id: 4
data: {"message_id":"m_2","text":"## How a National AI Strategy Is Structured\n\n"}

event: done
id: 57
data: {"message":{"id":"m_2","status":"complete","content":"## How a National…",...}}
```

## 6. Open questions for the backend

1. Can the backend generate conversation titles automatically? Is lazy conversation creation (`/conversations/new/messages`) acceptable?
2. Model and effort selection: is it supported (`/models`), or is there a single fixed model?
3. Audio storage and playback: signed URLs (S3, GCS or Azure) or an auth-protected streaming endpoint? What is the URL TTL?
4. Which transcription provider, and is transcription synchronous inside the message stream (as proposed)?
5. Vapi: custom-LLM pointing at our backend, or a Vapi-hosted model? Who owns the assistant config?
6. Rate limits per user, and the per-message size limit (proposed: 32k characters).
7. Is stream resumption (`Last-Event-ID`) in scope for v1?
8. Is there a reverse proxy in front of FastAPI? It must not buffer `text/event-stream`.
9. Regenerate: does it replace the assistant message in place (as assumed), or keep previous versions?
10. Attachments (§4.7), feedback (§4.8) and artifacts (§4.9): which are in scope for v1, and are the limits above right?
11. Will the backend emit a distinct `solving` status, or only `thinking` / `answering`?
